# 0.9.3：SOP 是可选方法，不是所有任务的前置门槛

[English](OPTIONAL-SOP.en.md)

## 原则

Playbook 只在**有明确适用的专用方法**时接管任务。没有专用 SOP，并不意味着任务不能执行；Harness 应继续遵循用户指令，使用原有工具、权限、安全策略和上下文完成工作。

`task-intake` 不再是“任何未知任务”的强制兜底。它保留给用户明确要求规划、拆解、定义验收或结构化接单的场景，也可以由用户手动 `/playbook start task-intake`。模型不能因为找不到更好的流程，就自行强制套用它。

## 选择语义

- `match`：存在唯一、完整且明确适用的方法，可以启动 SOP。
- `ambiguous`：存在多个完整匹配的方法，需要当前 Agent 按交付目标选择；必要时只追问真正缺失的信息。
- `passthrough`：没有完整匹配。Playbook 不创建 Run、不阻止工作工具，Harness 正常执行用户任务。
- `conversation`：普通问答/闲聊，不使用 SOP。

“插件”“model”“视频”等词只产生候选提示，**部分关键词命中不构成 SOP 适用性**。例如“把 model-mgr 这个插件删了吧”可以部分命中插件开发与模型部署词汇，但交付物是卸载已有插件，因此应 passthrough，而不是开发、部署或 task-intake。

## 边界

passthrough 只发生在尚未启动 Playbook 时。已经挂载的 SOP 仍固定自己的阶段、Gate、返修和权限规则，不能借“没有匹配”逃避正在执行的验收。Playbook 不扩大 Harness 权限。

一个 passthrough 任务不会污染下一条用户任务；原生 `ask_user_question` 的真实澄清仍会与当前任务合并。

0.5.0 起支持项目 SOP 的创建与复用，但“当前没有 SOP”本身不是自动生成新方法的理由。一次明确、低复杂度操作更适合直接执行；只有任务确实反复出现、方法值得固化，或者用户要求建立流程时，才整理/保存 SOP。

测试覆盖插件卸载、未知维护、部分关键词候选、后续新任务不继承、真实歧义仍受保护，以及用户明确手动启动 task-intake。测试不证明外部卸载动作已在用户机器完成。
