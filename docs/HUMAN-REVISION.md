# 0.7.4：用户返修不是模型重试

[English](HUMAN-REVISION.en.md)

## 修复原因

旧版把 `delivery.maxRevisions=2` 当成用户的硬性返修次数上限：第三次明确退回仍会报 `User revision budget 2 reached`，并要求新建任务。与此同时，64 次 Gate 提交与 self-repair 次数按整个 Run 累加，单独删除“2”仍可能在后续检查再次卡住。这是预算分类错误，不是用户缺少授权。

## 当前规则

**用户明确要求返修不设固定次数上限。** 第三次、第四次以及后续退回都保留原 run/session、工作目录、SOP 快照、素材、既往候选和审核意见，进入原流程的下一次 revision。重复投递的同一用户消息不重复计数；过期 UI 候选仍不能操作新候选。

**自动尝试仍有边界，但按“本次用户指令”计费。** 默认每轮最多 64 次正式 Gate 提交，自动 repair 继续使用该 SOP 的 maxSelfRepairs。新的直接用户退回开始新的一轮自动工作额度，不删除过去的提交、失败、修复或成本记录。repair、recover、check、status、reload 和模型自报的“用户授权了”都不能产生这个边界。

`workBudget` 同时提供本轮使用量/剩余额度、整个 Run 的累计次数，以及 `userRevisions.limit=null`。报告中的 gatesPassed/gatesFailed/selfRepairs/revisions 仍是累计事实，不能用本轮计数假称“一次就成功”。这些是次数预算，不是 token、费用或墙钟时间预算；宿主其它费用/权限限制继续生效。

## 自动额度用完后的原任务续做

真正的自动重试额度耗尽时，Agent 应说明具体进展和卡点，停止无效循环，不建议取消、清状态或绕出 SOP。用户直接说“继续原任务”即可在**原阶段、原 Run、原 revision**开启一轮有界自动续做。候选仍在 awaiting_review 时，这句话不会替用户否决候选；需要明确的退回意见。缺权限/资料的 blocked、已取消任务也不能借续做跳过前置条件。

自然语言续做只识别明确短句（例如“继续”“继续原任务”“继续生成 v4”）；含糊或复杂意见仍应正常解释而不是强行授权。人类命令 `/playbook continue` 是可选替代入口，不是日常前置步骤。模型工具中没有 continue/reset_budget/reject/accept 的自助授权入口。

新的用户指令会使旧工具回执失效并隔离迟到结果，但不删除已确认产物或默认重新生成。受控修复仍应只处理实际受影响的内容，所有 Gate 照常检查。

## 兼容与使用

修复是运行层预算语义，不要求用户修改批准过的 SOP。旧快照里的 `maxRevisions: 2` 留作历史兼容信息，不再限制当前用户；新定义默认 null。项目方法的静态对比忽略这一个已废弃字段，仍严格保护真实 Gate、工具策略、阶段和自动 repair 上限。不会因为升级补丁就强迫重新批准同一套方法。

先备份实际状态文件，再用原服务账号和相同 DSH_HOME 更新并重启原 Profile：

```bash
dsh plugin --profile web add github:rffanlab/dsh-playbook#main --force
```

回到被“两次上限”卡住的原会话，直接重新发送之前的退回意见，例如：

```text
拒绝候选，按刚才明确的修改意见继续，其余已确认内容不变。
```

不取消、不新开、不清状态、不扩大 QC 例外。`runtimePluginVersion` 应为 0.7.4，固定的 `run.playbookVersion` 不必变化。本版本不会静默重放补丁安装前未登记的反馈，所以重发原意见仍有必要。

## 验证与边界

回归覆盖第三次/多次真实用户 pre-step、旧 maxRevisions=2 快照、累计超过64次提交、跨多轮自动修复、状态重载、落盘失败、并发去重、超过短 ID 缓存后的重投递、明确续做、模型/引用伪造不续费、旧 UI 目标拒绝、质量不合格仍失败。

这里只改变预算作用范围，不改声学阈值、媒体检查、文件归属、项目规则、权限边界或自主批准能力。没有重新调用真实模型、访问 E5 或制作视频。旧 docs 中“全局64次/用户最多2次”是历史版本说明，本页和当前状态的 workBudget 为最新口径。
