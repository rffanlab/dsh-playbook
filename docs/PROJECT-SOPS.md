# 0.5.0：项目 SOP 方法库与先读后选

[English](PROJECT-SOPS.en.md)

## 日常使用

更新 main、重启原 DSH Profile，开新会话直接交任务书。无需每天手动指定 SOP 或填写 JSON。

```bash
dsh plugin --profile web add github:rffanlab/dsh-playbook#main --force
```

预期过程：Agent 用已有 read/grep/glob 等工具读取真实任务资料 → `intake_status` 查看读回执与当前工作目录已有项目 → `intake` 登记项目及本次要求 → 复用项目 SOP，或 `sop_validate` / `sop_save` 派生试用方法 → `route` 执行。简单、没有文档引用的非视频任务仍可直接匹配；视频和引用任务书的任务不再仅凭关键词开工。

道家文化讲解新增独立基础流程 `taoist-culture-video`，原文语境、释义边界和自然口播有独立阶段。B 站实验/教程恢复 `evidence` 阶段。共同的稿件覆盖、样片、音频和文件版本检查仍保留。现在是 20 个基础 SOP，但重点是项目自己的持久方法库，不是继续堆模板。

示例任务：

> 按这份道家文化任务书做今天的视频，保留已经给定的脚本和自然配音要求。视频发到 B 站，但内容仍属于道家文化项目。

> 按这份实验任务书做 B 站模型实测视频，保留方法、原始数据和未验证项。

Agent 根据正文和项目判断，不能把发布平台当成业务流程。缺真正的任务资料时才追问。`只写视频脚本` 不应强制交付完整视频。主题、时长和本次输出目录应放进 run input；同一方法换一期主题不应重复建 SOP。

## 保存、试用与确认

- `trial`：继承基础流程的正式要求，增加项目说明/稳定规则。可以在所属项目中试用，不冒充专家验证。
- `draft`：删除/改写原有阶段、目标、执行模式、工具策略、Gate、修订策略或已确认规则，需要人工审阅；不能直接 route。
- `approved`：用户确认的精确版本。成为该项目该逻辑 SOP 的当前默认。任务验收通过不会自动把 SOP 升为 approved。

新版本不可覆盖旧定义。保存后产生完整 revision 标识与定义摘要，运行时嵌入快照。已确认项目方法不能被同类通用模板、换名试用稿或旧 approved 版本自动替换。正在执行、失败待修复、等待验收的任务不能用 intake 更换项目或要求；使用既有 repair/revise 路径。

需要确认一套方法时，在 Web 设置的 Playbook 面板查看“当前项目 SOP”，打开具体版本、查看规则与差异，再点击“确认此精确版本为项目默认”。这不是每次执行的审批。命令等价入口：

```text
/playbook project
/playbook sops
/playbook sop <sop-id> <revision>
/playbook approve <sop-id> <完整revision>
```

`approve` 只在人工命令/面板提供，不是模型工具 action。审批检查原 approved 父版本，防止过期提案覆盖新决定。切换了会话后，面板要求重新查看，不跨会话批准旧视图。

项目按 **宿主 session cwd + project_id** 隔离，不取模型提供的目录、不退回进程 cwd。一个目录可有 culture、bilibili-ai 等多个项目；会话绑定后模型不能随意改名。确实要在同一目录建第二个独立同类项目，用户可明确 `/playbook project use <id>`；已有运行需先完成或取消。目录身份采用宿主绝对路径的规范化拼写，不做跨符号链接别名自动合并；此隔离是方法选择范围，不是多租户文件权限系统。

## Agent 接口（用户不用手填）

先读文件。宿主最终 read 回调中的 callId 可从 intake_status 查到。

```json
{"action":"intake","project_id":"taoist-culture","requirements":["保留给定原文与脚本","自然语速，不为目标时长变速"],"source_call_ids":["真实read调用ID"]}
```

```json
{"action":"sop_save","sop_id":"culture-production","base_id":"taoist-culture-video","name":"道家文化栏目制作","rules":["核对原文、出处和释义边界"],"stage_notes":{"source-truth":["使用任务书指定的原典版本，现代应用要明确标注。"]}}
```

```json
{"action":"route","sop_id":"culture-production"}
```

`sop_list` / `sop_inspect` 查询当前项目；`sop_validate` 只校验，不写状态。`sop_save` 可接收完整 `definition`；改动受保护部分时保存为 draft，不通过改名逃避。重复保存同一方法会复用已有记录，新的单期源文档不会单独制造一个方法版本。全新、与基础图不同的工作方法可以起草，但图和保护规则变动需一次明确审阅，不能由执行模型自行宣布等价。

## 读证据与信任边界

只从成功、受宿主权限控制的 `read` 工具最终 canonical result 收集回执。引用任务文档时至少需要真实回执，分页必须覆盖声明的行范围；不能用一个“已读”布尔值代替。暂不把 PDF、图片 OCR、网页或其它插件格式认证成完整文本任务书回执；Agent 可用它们辅助发现，但此版本的强读取入口是 UTF-8 read。必要时提供对应文本版本，不伪称读过。

回执摘要是**返回文本窗口**的 SHA-256，不是原文件字节摘要；宿主截断长行、文件在不同分页之间被修改、Agent 是否理解内容/选对来源，都不能由这个回执证明。保留完整用户任务、本次提取的要求和读回执来源供复核；提取要求是否穷尽正文仍需语义审核。

静态保护比较采取保守策略：不猜“这次改写是不是同义”。新增文字也可能与旧要求冲突；trial 不能被视为独立语义验收。正式任务的模型执行能力、最终作品质量及 SOP 方法是否适合，仍需真实实验。

批准门禁、版本摘要与作用域防的是管理接口中的误改/混用；**不是恶意代码或拥有相同文件写权限的 Agent 的隔离沙箱，也没有签名防篡改**。Host 自身权限、只读/可写目录配置仍需正确设置。

## 存储与迁移

项目库保存在原 playbook-state.json 的 `sopLibrary`，状态格式 v3，读取兼容 v1/v2。运行快照、返修记录与旧档案保留。一个项目最多 100 个不可变版本；不是无限历史库。多进程不能同时写同一个文件。

新安装仍只用既有工具和模型，不加 API Key/向量库。原有媒体依赖和技术阈值未更改；自定义项目不能通过注册接口删除检查来跳过当前任务。

**兼容变化：** `~/.dsh/playbooks/*.json` 中与内置同名的全局覆盖会警告并忽略，防止 `reload` 改掉基线；其它旧自定义 ID 仍保留原全局加载行为。旧全局定义不等于已确认的项目 SOP，应通过管理接口迁移。不要让模型写这个目录来替代 sop_save。

升级前备份状态文件；旧已运行任务继续固定旧定义，不自动获得新流程或项目绑定。回退旧版本前恢复相应状态备份，不让旧写入器覆盖新库。

## 验证范围

测试覆盖：读前选流拦截、只读发现放行、分页/虚假读回执、项目/目录隔离、同平台不同内容图、试用保存、跨模型复用、不可变版本、弱化差异、审批/父版本冲突、换名绕行、冻结运行、磁盘失败回滚、同名旧覆盖阻断、实际 SDK schema 与媒体回归。测试用匿名合成任务，不上传私有任务书或会话。

没有重新调用 MiniMax，也没有远程接管用户 E5。单测、SDK 契约与打包检查不替代目标 Web Profile、实际模型的端到端验证。
