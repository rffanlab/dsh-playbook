# 0.7.2：恢复调用不要被接单流程再次拦住

[English](RECOVERY-DISPATCH.en.md)

## 复现到的故障

在 0.7.1 的完整 Host 插件接线上复现：保留一个符合 manifest-base 恢复条件的 failed Run → 接收“继续生成 v3”这类直接用户消息 → pre-step 误设为待接单 → Agent 调用 recover → 固定只读 Bash 探针通过运行状态检查，却被独立的 intake Guard 拒绝。

此前的恢复冒烟直接调用 recover，漏掉了它前面的真实用户续做入口。因此单独恢复测试通过，不能说明接在聊天流程上也能工作。本轮在原代码重现拒绝，在修复后验证完整顺序。夹具匿名合成；用户这次提供的是对话摘录，不是新增的完整运行日志，不能据此排除部署上还有其他宿主限制。

## 修复

- 已识别插件事故或 failed Run 收到继续任务时，保留原 Run 的恢复路径，不再注册一条新的 intake。识别到适配事故时先恢复，不把重复返修指令又算成一次用户修订。用户原消息保留在对话里，不删除资料、清空历史或自动生成新任务。
- 同一份“插件内部已登记的控制调用”识别同时用于本插件的运行 Guard 与接单 Guard。recover 的例外要求完整匹配 callId、Agent、parent token、rootCallId 和全部参数；调用结束立即撤销。更改命令、workdir、超时或添加提权参数不能借用例外。
- 这是协调本插件内部检查，不是忽略其他插件或宿主规则。隔离目录、真正的 Host 权限、沙箱和取消信号仍生效；没有改 /opt 下的宿主实现，也没有裸 Shell 回退。
- 恢复探针失败时返回 hostFailure，保留该次 callId、实际错误码与消息，并区别工具错误、超时、退出码非零、后台结果和无效返回。不会把所有错误都称为“缺少授权”。输出是有界摘要，不复制整个命令或 stdout/stderr。
- 紧凑响应不再把明确的 report_actual_host_failure 改写成 recover，避免提示模型重复撞同一个错误。真正的拒绝仍需原权限机制处理，不提供“直接在 SOP 外出片”的替代路径。

只读探针真正成功后，仍然是原 Run 原阶段恢复，不是 Gate 通过。原预算、候选、文稿要求、模型身份和修订历史保持；实际制作与 QC 仍需通过相应规则。0.7.1 的事故恢复标识刻意保留，已完成的恢复不会仅因补丁版本更新重复登记。

## 更新及版本确认

用原服务账号、相同 DSH_HOME 更新并重启原 Profile：

```bash
dsh plugin --profile web add github:rffanlab/dsh-playbook#main --force
```

回原会话正常说“继续生成 v3，保留已批准文稿与素材”。这是继续已授权任务，不需要额外同意删除记录、重建 Run 或绕开 SOP。

模型的 playbook status 返回和人工 `/playbook status json` 增加 `runtimePluginVersion`。本补丁应为 `0.7.2`。`run.playbookVersion` 是固定的方法版本，可能仍为 0.4.0/0.7.0；不要拿它判断实际加载了哪个运行补丁。

如果实际权限仍拒绝，报告具体 hostFailure，而不是再让用户从“清空/退出 SOP/修改宿主”中三选一。升级插件并不保证外部权限或所有内容问题都不存在。

## 验证边界

新增全 Guard 链回归覆盖：用户续做、旧 pending 残留、原任务身份与预算、真实外部拒绝不被覆盖、8 类伪造/改参数调用被拒、错误码/下一步不被紧凑化吞掉。原 CI 的隔离冒烟增加用户 pre-step，再经模拟 Host 调度执行真实 Python 读取及正常 Gate 提交。

状态格式和 SOP 定义未改，未增加依赖。没有远程操作 E5，没有调用 MiniMax/Qwen 生成新作品。源码回归与 CI 成功不能冒充 v3 已经制作、试听或验收完成。
