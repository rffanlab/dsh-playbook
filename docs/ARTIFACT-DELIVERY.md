# 0.9.0：验收产物与最终附件使用同一份登记

[English](ARTIFACT-DELIVERY.en.md)

## 修复的是哪一层

此前的独立 Run 路径、实际媒体检查和已知旧哈希对照是真实代码，不只是 Prompt。但它们主要在阶段 submit 时生效。0.8.0 的插件 Guard 没有核对最终 `present.files` 是否来自这个 Run 的候选；DSH 的原生 present 检查文件存在后保存路径，不保存当时的字节。验收 A、交付 B，以及交付后工作文件被覆盖，是不同于媒体 QC 的缺口。

源码夹具已经复现：候选在当前独立目录，原 Guard 链仍不拒绝 `/workspace/old/final.mp4` 的 present。此结果证明代码缺口，不证明某次真实事故的唯一来源。文件同哈希/二进制相同只证明字节相同，仍要用本轮 Session、候选记录、present 路径和下载映射定位历史原因。

## 正常流程无需用户管理文件 ID

新视频任务继续使用现有项目方法和独立 Run。Agent 在最后组装时调用：

```json
{"action":"build","command":"python3 work/render.py","output_paths":["final/final.mp4"]}
```

这是现有 Bash 命令的受控调用入口，不是新的渲染引擎。固定检查器先观察这些确切输出是否存在和它们的哈希，再通过原 Agent、父调用、取消信号、工具策略运行命令，随后重读实际输出。只有前台正常完成的实际命令才能登记；后台任务接受回执、非零退出、缺文件、无关 echo/true、只改变假文件但旧视频没变，不能被当成新成片。默认前台超时 120 秒，可用 timeout_ms 在 1～600 秒内指定，宿主本身的超时与权限仍然生效。长时间素材生成继续使用原工具；此入口面向最终组装。

同 Run 已有命令证据、且字节不变的文件可以复用，不为凑时间戳而反复重新生成。新任务的 video/handoff Gate 要求最终视频哈希与本轮命令观察对应，仍然执行既有音频、全文、字幕、归属和 QA 检查。命令登记不等于 QA 通过。

最终 Gate 通过后，插件自动执行交付。如果仅交付 IO/宿主 present 出错，保留已通过的 QC 与准备好的副本；Agent 用 `playbook(action="deliver")` 重试交付，不重新做片、不让用户挑一个旧文件。

## 交付链

```text
当前 Run 的候选 key
→ 系统登记的 artifact ID、源路径、哈希和实际清单
→ 重读并核对源文件字节
→ 新建本 Run 下的 .deliveries/<随机UUID>/
→ 独占写入副本并重新计算哈希
→ 通过原 Host present 交付这些副本
→ 核对实际 present 结果及副本仍一致
→ 保存 prepared/presented 交付记录
```

没有按文件名搜索最终产物的逻辑。`final.mp4` 只是可选的工作文件名，不能替代登记。视频、封面、规范稿、标题、字幕从已验收清单的明确引用取得；另附系统报告和 delivery-receipt.json。Agent 可选附加一份本 Run 的文字报告（extra_paths），该报告标为 auxiliary-report，不作为 QC 或生成事实来源。默认七个附件，带辅助报告最多八个，兼容原生 present 默认上限；宿主若设置更小上限会如实返回拒绝。

每个记录包含 run/session、候选修订、artifact ID、源路径、实际 SHA256/大小、命令 callId/指纹（有记录时）、交付副本路径、实际 present callId。系统报告不采纳模型手填的“我生成过”作为证据。状态中的 `artifactDelivery` 与模型 `artifacts` 动作可以查看真实登记。

直接用 present 指向旧目录/另一个 Run 的视频会拒绝。最终候选应走 deliver，而不是要求用户额外授权。普通编码、文档、仅音频等非媒体生产流程不会因此被绑定视频要求；当前 Run 非最终图片/文档预览仍保留。未知第三方附件工具不被声称已经覆盖。

## 已知历史文件与源文件覆盖

状态增加持续保留的已知视频摘要索引，不再完全依赖最近 20 个运行档案。复制已记录旧视频到新目录、更新修改时间，仍不构成独立新结果。已有用户登记的 exclude-hash 继续有效。索引来源为本插件已有/新记录，不扫描全部硬盘，也不公开用户的视频或哈希。

交付副本使用唯一目录、独占创建，并设置普通只读权限。本插件不覆盖已经交付的副本；工作区源文件随后改变，不会改变那份副本。此设计减少同名路径和后续覆盖导致的串台。副本会占磁盘空间；本版不会自动清理历史文件或替用户删除素材。

## 兼容与权限

更新后保留原 Run、SOP 快照、候选、项目方法和历史。旧 Run 没有可追溯的生产命令记录时，不凭空补写；可以在有真实候选绑定和既有隔离/兼容范围时交付固定副本，报告明确 producer 缺失。若缺少清单/候选绑定，先按已有机制复核原文件，不搜索猜测路径。新 Run 才要求最终组装 witness；并不会为了升级强迫旧作品重做。

这不是授予任意 Shell 权限。固定文件操作的例外只对本插件自身登记的完整参数、Agent、parent/rootCallId 生效；实际生产命令没有该例外。其他 Host Guard、沙箱拒绝和取消均保留，无裸 Host 文件读写 fallback。模型也不能凭空批准或修改用户验收状态。

## 必须保留的边界

- 命令前后观察证明执行与字节变化的关联，不是逐文件生成因果证明，更不是模型作者签名。任意脚本仍可能复制未知旧文件；并发同用户进程也可能改写文件。
- 哈希识别已知完全相同字节，不识别重新编码/语义复制。未知旧产物不会凭空进入摘要索引。登记来源不足时应标明未建立独立性。
- .deliveries 的只读权限不是抵御同用户恶意进程的沙箱。原生 DSH 仍按路径提供文件；本插件只对自己的固定交付路径和交付时字节做保证，不声称已审计第三方下载服务或浏览器缓存。
- 本修复覆盖带媒体验证器的生产 Run。没有选中相应生产方法、插件没加载、通过其他扩展/HTTP/手工粘贴交付的内容，不在这个出口检查覆盖内。代码＋视频复合任务仍应明确各自执行范围，不宣称一套工程 SOP 自动拥有视频验收。
- 没有新增 ASR、视觉质量评分或 E5 实机验证；不把技术测试通过等同于模型交付质量提高。

## 更新与验证

```bash
dsh plugin --profile web add github:rffanlab/dsh-playbook#main --force
```

使用原服务账号、原 DSH_HOME；更新前保留实际状态备份，重启原 Profile。runtimePluginVersion 应为 0.9.0；旧方法版本可以不变。无需取消、清状态、再批准同一 SOP。是否重做视频取决于本轮真实产物与证据，不是为了通过本次插件升级。

测试包括原 Guard 缺口复现、真实子命令执行前后输出、错误/外部拒绝/无变化、候选被替换、已知旧哈希、实际快照、交付重试、非媒体不受影响与持久化。Python/FFmpeg 使用合成媒体检查完整稿/音轨/字幕，再验证副本和源文件覆盖。scripts/delivery-smoke.mjs 跑实际 FFmpeg → 实际 QC → 自动快照 → 模拟 Host present，全链条保留同一 Run。仍不是实际 E5/浏览器/生产模型端到端测试。
